## Backup before editing an official Doc

1. Identify the current canonical target and inspect every tab, table, native control, field and source prompt.
2. Make a full native copy before the first official-document mutation. A new assignment adapted from a template is a new canonical target; later edits to that target require their own backup.
3. Give the backup a clear name such as `[Current title] — BACKUP before [change] — [actual date/time IST]`. Do not reuse an older backup as if it captured the latest pre-edit state.
4. Verify the backup exists and retains the source's complete native structure/content. Record canonical ID, backup ID, actual time and change scope in the work's review record.
5. Keep the backup noncanonical. Website homework actions must continue to point to the official target unless an explicit migration is authorized.
6. Apply the requested change, read back all affected structure/text and compare official prompt/instruction text against the source/backup. Refresh live indexes after structural edits. Avoid transformations that delete the opening characters of checklist items.
7. Inspect page flow, answer fields, checkboxes and avatar placements in the actual native result and rendered pages where required. If an edit damages text, restore the affected material from the verified backup without discarding unrelated student work.

Preserve every official instruction, prompt, factual detail, existing table dimension and submission requirement. Keep student answers intact. A rollback must be scoped and reviewable; never delete or overwrite an entire document just to repair one field.

## One canonical homework destination per assignment

- `library/schedule.js` owns the current official homework URL. Both beginning/end Homework Doc actions on the playbook must resolve to that same document ID.
- Session guides link to playbooks; homepage assignment cards link to the playbook's `#share`. Direct Homework Doc links occur only on playbooks. Do not add an HTML homework page.
- Audit schedule records, public HTML, lesson content/runtime data and generated resource destinations for stale or noncanonical IDs. Rebuild affected generated resources when lesson source changes.
- Backup URLs and student-copy URLs belong in author/review records, not website homework actions or the release schedule.
- Several URL suffixes can point to the same native document; compare the actual document ID, not only the literal string. Preserve supplied copy/edit behavior rather than silently forcing a `/copy` URL.
- Preserve meaningful duplicates and student work in Drive. Remove stale site references where needed; do not permanently delete Drive files without explicit user direction.
- Future homework navigation follows the existing scheduled start. The site's locks do not secure Drive sharing. Never replace an unavailable canonical Doc with a backup merely to make a link open.

## Approved prototype workflow and controls

For a new overall visual/control pattern, apply it to one representative Doc with a backup and obtain review before a broader rollout. The 8 October prototype already approved Inter/orange/charcoal/warm-white styling, shaded blank answer space, three to five purposeful right-side inward-facing avatars and native checkboxes. Reuse that pattern without asking for the same approval again. An explicitly supplied native template or current user direction governs any difference.

Use native dropdowns only when the available authoring tools can create and verify them. The approved prior rollout used native checkboxes because dropdown creation was unavailable. Recheck actual capabilities for a future task; do not treat that dated limitation as permanent. Do not fake a dropdown, silently replace it with styled text or create a companion Sheet unless requested.

## Review record to keep

Record the canonical Doc and backup, all tabs inspected, preserved source prompts, changed answer areas, actual checkbox/dropdown behavior, each avatar's role/position, rendered-page evidence, canonical site-reference checks and access limitations. Distinguish native readback from visual verification; a successful export or thumbnail alone is not a page-layout pass.
